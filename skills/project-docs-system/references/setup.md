# Создание и адаптация

## Изучить проект

Используй порядок начала из SKILL.md. Недоступный источник отметь;
не заполняй его содержимое догадками.
Короткая карта «назначение → существующий документ → нужное изменение»
помогает выбрать объём. Храни карту в навигации, если она нужна и после переноса.

## Новый проект

Начни с одного README: цель и границы, нужные источники, текущая задача,
способ проверки и следующий шаг. Например, для небольшого каталога книг
критерий CSV-импорта, ожидаемую ошибку и статус «не проверено» можно описать
разделами того же README. Отдельные spec, test case и журнал не обязательны.

Разделяй материалы по правилу выбора файла из SKILL.md. При росте проекта
могут понадобиться навигация, контекст, процесс, описания задач и решений,
проверки и история. Создавай папку вместе с первым нужным материалом.
Отдельные DoR/DoD нужны только при полезном различии входных и выходных критериев.
Шаблоны выбирай по задаче, убирай неприменимое и обозначай неизвестное.

Init — инструкция переноса системы в другой проект. Создавай его, когда
такой перенос входит в задачу или предусмотрен действующим процессом.
Обычному проекту отдельный init не нужен.

Для контекста, навигации, процесса, init и правил ассистента есть
[заготовки](../assets/workspace/). Это исходный материал для адаптации.
В конечных документах относительные ссылки должны указывать на целевой проект.

## Существующий проект

Установи соответствие функций уже имеющимся материалам: requirements вместо
features, ADR вместо decisions, журнал в CHANGELOG вместо work-log допустимы.
Расширь подходящие документы точечно. Новый шаблон не заменяет действующую форму
без причины. Противоречие между источниками фиксируй с их статусом и владельцем
решения; предложение по устранению не объявляй внедрённым правилом.

При повторном применении используй правило из SKILL.md: без новой потребности
изменения и запись в журнал не требуются.
Архивирование или массовые перемещения рассматривай как отдельное изменение
в пределах поручения. Сохрани доступ к историческим результатам.

## Первая задача

Выбери реальную задачу пользователя. Опиши цель и критерии, существенный выбор
оформи decision при необходимости. Подготовь проверку каждого критерия,
свяжи её с требованием. Проведи разрешённые доступные проверки; недоступные
пометь «не проверено» и укажи причину. Запрос на организацию документации сам
по себе не требует реализовать описываемый продукт или выполнить операцию
во внешней системе. Зафиксируй результат именно выполненного объёма.

## Передача ассистенту

Используй существующие инструкции среды; добавь ссылки на навигацию и рабочий
цикл, порядок чтения и обновления. Если инструкции не подхватываются средой,
объясни, какой файл пользователь должен передать явно. Правила проекта должны
оставаться доступными и при работе без установленного скилла.
