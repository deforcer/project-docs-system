# Назначение документов и связи

## Выбор формы

| Форма | Когда нужна | Что хранить |
| --- | --- | --- |
| Feature/spec | Самостоятельное значимое изменение | Проблема, результат, границы, требования, приёмка, проверки |
| Decision/ADR | Существенный выбор с последствиями | Контекст, варианты, решение, основание принятия, пересмотр |
| Note | Небольшое наблюдение или уточнение | Вывод, основание, вопрос или следующий шаг |
| Test case | Воспроизводимая проверка | Требование, условия, шаги, ожидаемое, место результата |
| Procedure | Повторяемая работа | Входы, последовательность, проверки, выходы, сбои |
| Work-log | История значимых изменений | Краткая запись со ссылками на основные документы |
| Resume-контекст | Продолжение сессии | Текущее состояние, решения, неизвестное, следующий шаг |

Усложнившуюся note перенеси в feature с ссылкой из исходной записи. Небольшой
правке не нужна полная цепочка документов. Значимая задача связывает:
цель/требование → решение при необходимости → проверку → фактический результат.
Work-log указывает на эти материалы.

## Статусы

Сохраняй статусы целевого проекта. Если соглашения нет, предложи для feature:
Draft, Ready, In progress, Done, Blocked, Dropped. Для decision:
Proposed, Accepted, Superseded. Accepted требует известного основания принятия;
Superseded указывает замену. У Blocked должны быть причина и следующий шаг.
Статусы документов не заменяют состояние внешней системы задач.

## Источники и актуальность

Ожидаемое состояние задают требования; фактическое подтверждают проверка или
актуальная рабочая система. У каждого правила есть одно основное место хранения.
Для меняющихся фактов сохраняй источник, дату и существенные ограничения.
У архивного материала укажи причину устаревания и замену, если она есть.

Контекст проекта отвечает: зачем работаем, где границы, кто принимает решения,
какие материалы достоверны и что ещё неизвестно. Навигация показывает, где это
прочитать. Процесс задаёт рабочий цикл и условия перехода к следующему этапу.
DoR — достаточность входных данных; DoD — доказательства завершения.

## Предметные расширения

Подключай только разделы, нужные реальным задачам: QA — среды и регрессия;
разработка — архитектура и поставка; исследование — методы и источники;
организационная работа — роли и процедуры. Шаблоны не задают готовые метрики,
формулы, системы, корпоративные ограничения или обязательные согласования.

Для повторяемого анализа полезны четыре связанных материала: методика,
объяснение результата читателю, инструкция запуска, результаты с датой и
условиями. Исторические результаты сохраняют свою версию методики.

## Имена и хранение

Выбирай принятую в проекте схему. Если её нет, для отдельных изменений подходит
YYYY-MM-DD-short-name.md, для постоянных правил — устойчивые имена.
Локальные ссылки должны переживать перенос проекта. В базе знаний используй
доступный механизм ссылок и одну основную страницу на правило.

Скилл не требует Git для целевого проекта. Выбери согласованное хранилище
с актуальной версией и историей значимых изменений. При Git краткую локальную
память исключают из коммитов; секреты и сырые чувствительные логи в документы
не помещают. Самого текста в беседе недостаточно, чтобы объявить файл созданным.
