# Project Docs System

Сделай документацию достаточной для работы и продолжения в следующей сессии.
Выбирай состав документов по реальной задаче и существующим правилам проекта.
Скилл хранит методику и заготовки; факты и результаты относятся к целевому проекту.

## Начало

1. Определи целевое рабочее пространство из запроса и контекста. Прочитай его
   правила для ассистента, навигацию, релевантные документы и последние записи
   журнала. Изучи структуру и доступные источники; при Git учти локальные правки.
2. Определи результат и пробелы. Используй место хранения из запроса или
   соглашений проекта. Если место нельзя определить или остаются существенно
   разные варианты, уточни его до записи. Роль и первую задачу выясняй, только
   когда они влияют на результат; не превращай начало в обязательную анкету.
3. Выбери режим ниже. Запрос на план заканчивается планом; запрос на внедрение
   включает создание или изменение документов и их проверку.

## Режимы

- **Создать:** в новом проекте выстрой минимальный каркас и проведи первую
  задачу через него. Читай [создание и адаптацию](references/setup.md).
- **Адаптировать:** сопоставь существующие документы с нужными функциями,
  сохрани действующие пути и добавь недостающее. Читай
  [создание и адаптацию](references/setup.md).
- **Сопровождать:** найди связанные документы конкретного изменения, обнови
  актуальные правила, результаты и контекст. Читай
  [сопровождение](references/maintenance.md).

Для выбора вида документа, связей и статусов используй
[методологию](references/methodology.md). Читай только нужные разделы.
Выбирай отдельные файлы из [шаблонов](assets/templates/); не копируй весь набор
автоматически. Для правил ассистента и переносимого init используй
[заготовки рабочего пространства](assets/workspace/).

## Рабочие правила

- Сначала переиспользуй документ с подходящим назначением. Названия `features`,
  `specs`, `decisions` и `ADR` могут отличаться; используй названия проекта.
- У правила должна быть одна основная версия; другие материалы ссылаются на неё.
  Не переноси корпоративные адреса, роли, метрики, workflows или разрешения из
  примеров. Правила Jira или других интеграций подключаются по контексту проекта.
- Начинай с существующего документа. Новый файл нужен, если материал полезно
  отдельно читать, обновлять или повторно использовать. Для малого проекта
  достаточно одного README; состав шаблонов не задаёт состав результата.
- Сохраняй пользовательские правки и договорённости. При повторном запуске
  сверяй существующее состояние, меняй только обоснованное; без новой потребности
  результат может быть «изменения не нужны».
- Предложение помечай как предложение. Основание принятого решения должно быть
  известно; не выдумывай согласование или ответственного. Сценарий проверки
  описывает ожидаемое, отчёт — фактическое. Незапущенную проверку отмечай явно.
- Постоянные факты и общий контекст продолжения храни в документах проекта;
  личные временные заметки — отдельно. Правила хранения смотри в
  [методологии](references/methodology.md#имена-и-хранение).
- Сохраняй материалы только в согласованном месте. Используй ранее выданные
  разрешения для того же объёма работы. Публикация и действия во внешних системах
  должны быть покрыты запросом или правилами целевого проекта.
- Инструкции ассистенту добавляй в поддерживаемое средой место со ссылкой на
  основные правила. Не считай, что любая среда автоматически читает AGENTS.md.

## Проверка и завершение

Проверь локальные ссылки, согласованность терминов и статусов, связь критериев
с проверками и результатов с доказательствами. Убедись, что файлы пакета не стали
местом хранения проектных задач и что материалы понятны без истории беседы.
Обнови затронутые материалы по [правилам сопровождения](references/maintenance.md).
Для незавершённой работы сохрани конкретный следующий шаг.

Покажи кратко: что создано или изменено, точку входа, выполненные проверки,
открытые вопросы и способ продолжить. Если доступны только сообщения,
выдай содержимое документов текстом и явно укажи, что файлы не созданы.
