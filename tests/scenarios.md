# Сценарии приёмки

Использовать временные рабочие пространства с синтетическими данными.
Ассистенту передать установленный skill и входной запрос, затем оценить
созданные файлы. Проверять смысл и сохранение данных, а не точные заголовки.

## 1. Новый проект разработки

Вход: пустая папка. Запрос: «Примени $project-docs-system. Я разработчик.
Проект — локальный каталог книг; первая задача — спецификация CSV-импорта,
критерий — понятное сообщение для строки без названия. Сейчас нужна документация».

Ожидается: минимальная навигация и контекст, правила, spec с критерием,
сценарий проверки, честный статус «не проверено» для ещё не созданного продукта,
место продолжения. Не нужны Jira/MCP, выдуманные роли или реализация продукта.

## 2. Существующий QA-проект и повторный запуск

Вход: docs/README.md, docs/requirements/login.md, docs/adr/environment.md,
docs/regression.md. Среда уже определена; в regression есть пользовательская
строка «Сохранять историю прогонов».
Запрос: «Адаптируй документацию. Сохрани текущие пути и регрессионную стратегию.
Первая задача — описать проверку восстановления доступа. Среда сегодня недоступна».

Ожидается: использованы requirements/adr, пользовательская строка сохранена,
новые features/decisions-дубли не появились, сценарий связан с требованием,
результат помечен «не проверено». Повтор без новых требований не меняет файлы
и не создаёт новую запись в журнал ради самого запуска.

## 3. Некодовый проект и сопровождение

Вход: README с целью — единый процесс заявок на обучение. Поручение:
«Организуй документы. Учёт в Markdown, согласует руководитель отдела.
Первая задача — описать процедуру обработки заявки; SLA ещё не согласован».

Ожидается: подходящая небольшому процессу структура, роль взята из запроса,
SLA — открытый вопрос, есть процедура и способ её проверки.
Затем дать изменение: «Срок ответа согласован — два рабочих дня;
обнови процедуру и связанные документы». Ожидается сохранение основания,
обновление сценария и журнала; старые результаты не выдаются за проверку
нового требования. Само описание не означает проведённый организационный пилот.

## 4. Границы и установка

- Запрос «Предложи план» не создаёт файлов в целевом проекте.
- Запрос «Поправь опечатку» не запускает реорганизацию всей документации.
- Если место хранения нельзя вывести из запроса и соглашений проекта или есть
  существенно разные варианты, ассистент уточняет его до записи. Очевидный
  действующий каталог документации использует без повторного согласования.
- При доступной только беседе явно сообщает, что файлы не созданы.
- Копия одной папки скилла работает без checkout исходного workspace.
- При существующей установке не заменяются пользовательские файлы.

Автоматическая проверка: `python3 scripts/validate.py`.
Семантические сценарии выполняются отдельно. Итог должен различать авторское
применение, независимый запуск ассистента и проверку самого продукта.

## 5. Переносимая установка

- У пользователя нет папки Projects; текущий рабочий каталог находится в другом
  месте. Установка через агента выбирает каталог клиента и не требует изменения
  структуры проектов. Ручная копия содержит весь пакет, исходный клон не нужен.
- В Codex пакет установлен как личный или проектный скилл; SKILL.md, assets
  и references доступны, ссылки пакета разрешаются в пределах установленной копии.
- В Claude Code marketplace регистрируется из корня репозитория, плагин
  устанавливается в user scope, пакет обнаруживается в стандартном skills/.
  В новой сессии ожидается команда /project-docs-system:project-docs-system.
- На компьютере установлены Codex и Claude Code. Промпт отправлен в Codex:
  установка и проверка выполняются только в Codex; Claude Code не настраивается.
  При отправке того же промпта в Claude Code ожидается обратное.
- Клиент невозможно определить из среды чата: ассистент уточняет его у пользователя
  до установки, а не устанавливает пакет во все обнаруженные программы.
- Установку папкой и плагином не дублируют; существующие пользовательские правки
  сохраняются. Расписание обновлений без запроса не создаётся.
- На Windows копирование папки не требует Junction; фактическую проверку на
  Windows отмечают отдельно от локальной проверки файлов.

Проверки упаковки: `python3 scripts/validate.py` и
`claude plugin validate .claude-plugin/marketplace.json`.
Проверку установки выполняйте в изолированной конфигурации клиента, чтобы
не менять личные настройки. Загрузку в новой сессии подтверждают отдельно.

## 6. Минимальный объём и место записи

Вход: пустая папка. Запрос: «Организуй документацию небольшого каталога книг
в README.md. Пока нужна только спецификация CSV-импорта: строка без названия
должна давать понятную ошибку. Продукта ещё нет».

Ожидается: цель, критерий, ожидаемое, статус «не проверено» и следующий шаг
помещаются в README. Отдельные process, work-log, init и resume не создаются
без потребности. Роль пользователя не выясняется ради заполнения формы.

Вариант: в проекте есть docs/README.md и соглашение хранить документацию в docs.
Запрос на адаптацию без указания пути использует это место без повторного вопроса.
Точечное уточнение существующего документа не создаёт служебные файлы.

## 7. Общая передача и личные заметки

Вход: Git-проект, docs/task.md с незавершённой задачей и notes/private.md
с личными временными заметками, исключёнными из Git.
Запрос: «Обнови описание задачи для передачи коллеге: CSV-импорт описан,
проверка ждёт тестовый файл; затем нужно проверить строку без названия».

Ожидается: состояние, препятствие и следующий шаг в docs/task.md доступны
коллеге через Git. Отдельный resume не дублирует задачу. Личные заметки
не включаются в коммиты; отслеживаемые файлы не удаляются автоматически.

## 8. Перенос системы по потребности

Обычная организация документации не создаёт init. Запрос «Подготовь перенос
этой системы в другие проекты» создаёт адаптированную инструкцию переноса.
При последующем изменении процесса используемый init обновляется вместе
с затронутыми материалами; отсутствующий init ради обновления не создаётся.

## 9. Источники, исследование и база знаний

- Два действующих источника противоречат друг другу: противоречие и основания
  видимы; ассистент не выдумывает принятого решения или владельца.
- Исследование с неизвестным исходом: гипотеза, источники, ограничения и следующий
  шаг сохранены; ожидаемый вывод не выдан за подтверждённый результат.
- Хранилище — база знаний без Git и файловых путей: используются её страницы
  и ссылки, сохраняются существующие названия; файловый каркас не навязывается.
  Для фактического прогона использовать изолированное разрешённое хранилище;
  разбор примера в беседе не считать проверкой интеграции.

Для сценариев 6–9 оценивать обоснованность новых документов, лишние вопросы,
сохранение исходных материалов и возможность продолжить работу по результату.
